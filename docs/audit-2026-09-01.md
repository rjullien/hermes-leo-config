# Audit fonctionnel, sécurité et performance

> **Dépôt audité :** `rjullien/hermes-leo-config` — **Date :** 1er septembre 2026 — **Révision :** `aa88129e37f133c2ef55fcdbbf673bfdc403a394` (`main`)
>
> **Périmètre :** Dockerfile, chaîne GitHub Actions/GHCR, Renovate, documentation et image reconstruite localement

## Synthèse exécutive

L'image est **fonctionnelle** : elle se construit et les cinq outils ajoutés (`gws`, `gh`, `kubectl`, `devin`, `go`) démarrent avec les versions attendues. Son surcoût CPU au démarrage est négligeable une fois l'image présente.

La principale faiblesse est la **chaîne de livraison** : Renovate peut fusionner sans build, sans smoke test et sans scan, tandis que les binaires téléchargés pendant le build ne sont authentifiés ni par checksum ni par signature. L'image finale s'exécute en root et hérite d'une surface importante de l'image de base. Un scan ponctuel a détecté deux vulnérabilités critiques corrigibles, toutes deux héritées de la base.

L'image ajoute environ **553 MB décompressés** (+20,3 %) et environ **168 MB compressés** au pull. Go et Devin représentent près de 78 % de cet ajout. Le cache Docker est sous-optimal : modifier une seule version invalide toutes les installations suivantes, voire précédentes selon la position de l'`ARG`.

### Verdict par axe

| Axe | Évaluation | Conclusion |
|---|---|---|
| Fonctionnel | Bon avec réserves | Build et smoke tests réussis ; contrat runtime partiellement externalisé |
| Sécurité | À renforcer en priorité | Pas de secret détecté, mais supply chain non vérifiée, root, CVE et absence de gate CI |
| Performance runtime | Bonne | Surcoût de démarrage faible |
| Taille et transfert | Lourds | +553 MB décompressés, environ +168 MB à télécharger |
| Exploitabilité opérationnelle | Non entièrement vérifiable ici | Manifeste, RBAC et secrets sont gérés dans `BaptTF/vps-infra` |

## Périmètre et méthode

Le dépôt ne contient pas de code applicatif : il étend [`nousresearch/hermes-agent`](../Dockerfile#L16) avec cinq outils, puis publie l'image dans GHCR via [GitHub Actions](../.github/workflows/build.yml).

Les vérifications suivantes ont été exécutées :

- lecture exhaustive des sept fichiers suivis et de l'historique Git ;
- reconstruction de l'image au commit audité ;
- exécution des cinq commandes de version dans le conteneur ;
- inspection de l'utilisateur, de l'entrypoint, du workdir, du volume et des couches ;
- exécution des outils avec filesystem read-only, sans capabilities et avec `no-new-privileges` ;
- tentative d'exécution en UID non-root ;
- scan Gitleaks de l'historique complet ;
- scan Trivy de l'image finale et de l'image de base, puis comparaison ;
- mesure des tailles de couches et estimation de leur compression ;
- benchmark comparatif de démarrage à chaud ;
- vérification des runs GitHub Actions, releases, PR Renovate et checks associés ;
- test d'invalidation du cache en changeant uniquement `GO_VERSION`.

Les CVE constituent un **instantané au 1er septembre 2026**. Elles doivent être rescannées au moment d'appliquer les corrections.

## Architecture et flux observés

1. Le [`Dockerfile`](../Dockerfile) part de `nousresearch/hermes-agent:v2026.8.16`.
2. Cinq binaires/toolchains amd64 sont téléchargés sous l'utilisateur root :
   - gws `0.22.5` ;
   - GitHub CLI `2.98.0` ;
   - kubectl `1.37.0` ;
   - Devin CLI `3000.6.7` ;
   - Go `1.27.0`.
3. L'entrypoint `/opt/hermes/docker/entrypoint-dispatch.sh`, le workdir `/opt/hermes` et le volume `/opt/data` sont hérités de l'image de base.
4. Une release ou un `workflow_dispatch` construit et pousse l'image dans GHCR.
5. Renovate s'exécute toutes les six heures et peut fusionner automatiquement ses mises à jour.
6. Le déploiement réel est piloté hors de ce dépôt, depuis `BaptTF/vps-infra` via ArgoCD.

## Constats détaillés

### F-01 — Aucun build de validation sur les pull requests

**Priorité :** P0 — élevée

Le workflow de build ne réagit qu'à `release.published` et `workflow_dispatch` ([`build.yml:3-6`](../.github/workflows/build.yml#L3-L6)). L'historique GitHub ne contient aucun run de ce workflow pour les événements `pull_request` ou `push`.

Les PR Renovate #8 à #11 ont été fusionnées avec **zéro check**. Une version inexistante, un changement de layout d'archive ou une rupture de l'image de base peut donc atteindre `main` sans que le Dockerfile soit construit.

#### Correction recommandée

Ajouter un workflow de validation déclenché sur `pull_request` et, idéalement, `push` sur `main` :

1. construire l'image sans la pousser ;
2. exécuter les cinq commandes de version ;
3. vérifier l'utilisateur, l'entrypoint et l'architecture attendus ;
4. lancer un scan de vulnérabilités ;
5. rendre ce check obligatoire avant merge.

Renovate peut conserver l'automerge, mais uniquement après succès du check obligatoire.

#### Critères d'acceptation

- une PR mettant `GO_VERSION` à une version inexistante échoue avant merge ;
- une PR valide produit un check vert sans publier d'image ;
- Renovate ne peut plus fusionner une PR dont le check est absent ou rouge.

### F-02 — Les identités `main`, release et `latest` divergent

**Priorité :** P1 — importante

Au moment de l'audit :

- `main` pointe sur `aa88129e` ;
- le dernier build manuel de `latest` a utilisé `899cbc0` ;
- la dernière release `v2026.8.31-c` a utilisé `e8265f7`.

La [release `v2026.8.31-c`](https://github.com/rjullien/hermes-leo-config/releases/tag/v2026.8.31-c), l'image `latest` et la branche principale ne représentent donc pas le même contenu. Le [build manuel concerné](https://github.com/rjullien/hermes-leo-config/actions/runs/33437496887) a réussi, mais il contourne le contrat « une release = une image » documenté dans le README.

#### Correction recommandée

- choisir une source de vérité : release immuable + digest OCI ;
- publier `latest` uniquement depuis une release, ou rendre le dispatch manuel explicitement incapable de modifier `latest` ;
- déployer par digest, pas par tag mutable ;
- documenter la convention des suffixes `-b`, `-c`, ou revenir au calver annoncé `vYYYY.M.D`.

#### Critères d'acceptation

- chaque image déployée est traçable vers un commit et une release uniques ;
- le manifeste GitOps référence un digest ;
- un dispatch manuel ne peut pas déplacer silencieusement `latest`.

### F-03 — Persistance des credentials Devin non démontrée

**Priorité :** P1 — importante

Le Dockerfile indique que Devin écrit sous `~/.local/share/devin/credentials.toml` et que ce chemin doit persister sur le PVC ([`Dockerfile:49-52`](../Dockerfile#L49-L52)). Or l'image observée utilise `HOME=/root`, tandis que le volume déclaré est `/opt/data`.

Le fonctionnement dépend donc d'un `HOME`, d'un mount ou d'une configuration externe non présent dans ce dépôt. En outre, un test en UID `65532` confirme que `/opt/data` n'est pas inscriptible sans préparation des permissions du volume.

#### Correction recommandée

Dans le dépôt d'infrastructure :

1. vérifier le chemin réellement utilisé par la version installée de Devin ;
2. configurer explicitement la persistance de ce chemin sur `/opt/data` ;
3. définir un UID/GID et un `fsGroup` cohérents ;
4. tester un redémarrage de pod après authentification.

Ne pas introduire de variable ou d'option Devin supposée : vérifier d'abord la documentation et le comportement de la version installée.

#### Critères d'acceptation

- l'authentification survit à la recréation du pod ;
- le conteneur n'a pas besoin de root pour écrire les credentials ;
- aucun credential n'est écrit dans une couche de l'image ou dans les logs.

### S-01 — Artefacts téléchargés sans preuve d'intégrité

**Priorité :** P0 — élevée

Les cinq outils sont téléchargés avec `curl`, puis copiés ou extraits comme root ([`Dockerfile:32-65`](../Dockerfile#L32-L65)). Aucun checksum, signature ou mécanisme de provenance amont n'est vérifié.

L'attestation générée par [`actions/attest-build-provenance`](../.github/workflows/build.yml#L58-L64) prouve ce que GitHub Actions a construit ; elle ne prouve pas que les archives téléchargées étaient les artefacts authentiques attendus.

#### Correction recommandée

Pour chaque dépendance :

- vérifier le checksum officiellement publié lorsqu'il existe ;
- sinon, versionner un SHA-256 attendu et faire échouer le build en cas d'écart ;
- préférer une signature/provenance officielle lorsqu'elle est disponible ;
- télécharger dans un fichier temporaire, vérifier, puis seulement extraire ;
- conserver les commentaires adjacents nécessaires au regex manager Renovate.

Le contrôle doit précéder toute extraction ou copie vers `/usr/local`.

#### Critères d'acceptation

- modifier un octet de l'archive fait échouer le build avant extraction ;
- une mise à jour Renovate actualise ensemble version et empreinte ;
- aucun artefact non vérifié n'est exécuté ou installé comme root.

### S-02 — Image de base et Actions référencées par tags mutables

**Priorité :** P0 — élevée

L'image de base utilise un tag ([`Dockerfile:16`](../Dockerfile#L16)) et les Actions utilisent des tags majeurs ou de version ([`build.yml:21-64`](../.github/workflows/build.yml#L21-L64), [`renovate.yml:29-38`](../.github/workflows/renovate.yml#L29-L38)). Un tag peut être déplacé : reconstruire le même commit peut alors exécuter un autre code ou produire un autre digest.

#### Correction recommandée

- référencer l'image de base avec `tag@sha256:digest`, après validation du digest `linux/amd64` ou de l'index multi-architecture voulu ;
- épingler chaque GitHub Action par SHA de commit ;
- laisser Renovate maintenir ces digests (`pinDigests` et pinning des Actions) ;
- vérifier l'attestation au déploiement si l'outillage du cluster le permet.

#### Critères d'acceptation

- deux builds du même commit utilisent les mêmes entrées identifiées par digest ;
- une mise à jour de digest apparaît explicitement dans une PR ;
- une action compromise par déplacement de tag ne modifie pas un workflow déjà committé.

### S-03 — Vulnérabilités corrigibles dans l'image

**Priorité :** P0 pour les critiques, P1 pour le suivi continu

Trivy `0.67.2`, base de vulnérabilités du 1er septembre 2026, avec `HIGH,CRITICAL` et `--ignore-unfixed` :

| Mesure | Image finale | Image de base | Ajout propre à ce dépôt |
|---|---:|---:|---:|
| Occurrences HIGH/CRITICAL | 125 | 123 | 2 |
| Identifiants uniques | 96 | 94 | 2 |
| CRITICAL | 2 | 2 | 0 |
| HIGH | 123 | 121 | 2 |

Les critiques héritées sont :

- `CVE-2026-33747`, `docker-cli` Debian ;
- `CVE-2026-59873`, package Node `tar`.

La couche de ce dépôt ajoute deux vulnérabilités HIGH dans le binaire `gh`, via `golang.org/x/mod` :

- `CVE-2026-56864` ;
- `CVE-2026-56865`.

La majorité du risque provient donc de l'image de base. Le nombre d'occurrences n'est pas équivalent au nombre de chemins réellement exploitables ; chaque critique doit être analysée selon l'usage effectif.

#### Correction recommandée

1. reconstruire sur une version de base intégrant les correctifs Debian et Node disponibles ;
2. mettre à jour `gh` vers une version reconstruite avec une version corrigée de `golang.org/x/mod` ;
3. générer un SBOM lors du build ;
4. scanner chaque PR et chaque image publiée ;
5. bloquer immédiatement les nouvelles vulnérabilités critiques corrigibles ;
6. adopter une baseline temporaire et datée pour le reliquat hérité, sans masquer les nouvelles régressions.

#### Critères d'acceptation

- les deux vulnérabilités critiques corrigibles ne figurent plus dans le scan ;
- aucune nouvelle critique ne peut être publiée ;
- le SBOM et le rapport sont rattachés au digest de l'image ;
- toute exception possède un propriétaire et une date d'expiration.

### S-04 — Exécution root et surface système importante

**Priorité :** P1 — importante

`USER root` est la dernière directive utilisateur du Dockerfile ([`Dockerfile:30`](../Dockerfile#L30)). L'image de base s'exécute également en root. L'image reconstruite contient 432 paquets Debian et 10 fichiers setuid.

Les cinq outils ajoutés ont cependant fonctionné lors d'un smoke test avec :

- root filesystem read-only ;
- `capabilities.drop = ALL` ;
- `no-new-privileges`.

Ce résultat montre que le durcissement est plausible, mais ne valide pas le runtime Hermes complet ni les écritures nécessaires dans `/opt/data`.

#### Correction recommandée

Dans `BaptTF/vps-infra`, tester puis appliquer :

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]
  readOnlyRootFilesystem: true
  seccompProfile:
    type: RuntimeDefault
```

Ensuite migrer vers un UID/GID non-root après préparation des permissions du PVC. Vérifier également que le service account utilisé par kubectl ne possède que les verbes et ressources nécessaires.

#### Critères d'acceptation

- Hermes et les cinq outils passent un smoke test sous le security context cible ;
- `/opt/data` reste la seule zone d'écriture persistante nécessaire ;
- le service account ne peut ni modifier ni supprimer les ressources si l'usage attendu est read-only ;
- aucun mount sensible de l'hôte n'est exposé.

### S-05 — Renovate a trop de latitude sans garde technique

**Priorité :** P0 — élevée

La configuration active l'automerge, vide les checks requis et ignore l'absence de tests ([`renovate.json:49-53`](../renovate.json#L49-L53)). Le workflow Renovate reçoit en outre un PAT (`RENOVATE_TOKEN`) ([`renovate.yml:35-38`](../.github/workflows/renovate.yml#L35-L38)). Les permissions déclarées pour `GITHUB_TOKEN` ne réduisent pas les scopes propres de ce PAT.

#### Correction recommandée

- limiter le PAT au dépôt et aux permissions strictement nécessaires ;
- le faire expirer et le faire tourner régulièrement ;
- supprimer `requiredStatusChecks: []` et `ignoreTests: true` dès que le workflow PR existe ;
- limiter l'automerge aux dépendances explicitement couvertes par des règles ;
- conserver un délai de stabilité pour la base et les binaires ;
- appliquer également un délai ou une politique de pinning aux Actions GitHub.

#### Critères d'acceptation

- aucune future dépendance n'hérite accidentellement d'un automerge global ;
- le PAT ne permet pas d'administrer le dépôt ou d'accéder à d'autres dépôts ;
- une PR Renovate attend obligatoirement le build et le scan.

### S-06 — Points positifs à conserver

- Gitleaks `8.28.0` : 29 commits et environ 22 KB scannés, **aucune fuite détectée**.
- Aucun secret n'est copié dans l'image par ce dépôt.
- Les permissions du job de publication sont déclarées explicitement.
- Une attestation de provenance est générée pour l'image publiée lorsque le dépôt est public.
- Les versions sont centralisées dans des `ARG` détectables par Renovate.

Ces garanties doivent rester actives pendant les corrections.

### P-01 — Taille d'image élevée

**Priorité :** P2 — optimisation

Mesures locales décompressées :

| Composant | Taille de couche approximative |
|---|---:|
| Go | 256,7 MB |
| Devin | 174,1 MB |
| kubectl | 61,9 MB |
| GitHub CLI | 41,4 MB |
| gws | 19,3 MB |
| **Total ajouté** | **553,3 MB** |

- image de base : `2 728 131 225` octets ;
- image finale : `3 281 443 460` octets ;
- augmentation : `553 312 235` octets, soit environ **20,3 %** ;
- compression gzip simulée des cinq couches : environ **167,5 MB** à transférer en plus.

Go et Devin représentent environ 78 % de l'ajout.

#### Correction recommandée

- confirmer que Go est nécessaire dans tous les pods et pas seulement pour les sessions de développement ;
- si l'usage le permet, publier une variante runtime et une variante `-dev` contenant Go ;
- conserver Devin dans l'image principale uniquement s'il fait partie du fonctionnement courant de Léo ;
- définir une politique de rétention GHCR et surveiller l'espace disque des nœuds.

Il ne faut pas retirer un outil sans vérifier les usages externes documentés dans `AGENTS.md`.

#### Critères d'acceptation

- chaque outil lourd possède un usage documenté ;
- la stratégie runtime/dev est explicitement décidée ;
- les temps de pull et l'espace image des nœuds restent sous les objectifs d'exploitation.

### P-02 — Invalidation excessive du cache Docker

**Priorité :** P1 — gain simple

Tous les `ARG` de versions sont déclarés avant toutes les installations ([`Dockerfile:18-28`](../Dockerfile#L18-L28)). Un test changeant seulement `GO_VERSION` a forcé le retéléchargement de gws, gh, kubectl et Devin avant d'atteindre Go.

Le dernier job observé a duré environ 90 secondes, dont 61 secondes pour le build et le push. Le cache GitHub est activé en mode `max`, mais l'organisation du Dockerfile réduit son efficacité.

#### Correction recommandée

Placer chaque commentaire Renovate et son `ARG` immédiatement avant le `RUN` correspondant :

```dockerfile
# renovate: datasource=github-releases depName=googleworkspace/cli
ARG GWS_VERSION=...
RUN ...

# renovate: datasource=github-releases depName=cli/cli
ARG GH_VERSION=...
RUN ...
```

Répéter ce motif pour chaque outil. Le commentaire doit rester adjacent à l'`ARG` pour préserver le regex manager Renovate.

#### Critères d'acceptation

- changer uniquement `GO_VERSION` réutilise les couches gws, gh, kubectl et Devin ;
- changer uniquement `GH_VERSION` ne reconstruit que gh et les couches suivantes nécessaires ;
- Renovate continue à détecter les cinq versions.

### P-03 — Architecture amd64 uniquement

**Priorité :** P2 — clarification

Les URLs du Dockerfile ciblent `x86_64`/`amd64` et le workflow construit uniquement `linux/amd64` ([`build.yml:56`](../.github/workflows/build.yml#L56)). L'image de base publie aussi une variante arm64.

#### Correction recommandée

- soit documenter explicitement que l'image custom est amd64-only ;
- soit utiliser `TARGETARCH`, vérifier la disponibilité de chaque binaire arm64 et construire une image multi-architecture.

#### Critères d'acceptation

- l'architecture supportée est visible dans le README ;
- si arm64 est activé, les cinq outils passent leurs smoke tests sur arm64 réel ou émulé.

### D-01 — Documentation désynchronisée

**Priorité :** P1 — importante pour l'exploitation

Exemples observés :

- le README annonce kubectl `1.31.0` et Go `1.23.6`, alors que le Dockerfile installe `1.37.0` et `1.27.0` ;
- `AGENTS.md` présente initialement trois ajouts alors que l'image en contient cinq ;
- le commentaire du workflow Renovate mentionne un réveil lundi à 08:00, absent du cron réel ;
- le flux documenté est centré sur les releases alors que `workflow_dispatch` peut aussi publier `latest` ;
- les releases suffixées `-b` et `-c` ne correspondent pas au calver strict documenté.

#### Correction recommandée

- éviter de recopier manuellement les versions dans plusieurs fichiers, ou ajouter un contrôle de cohérence ;
- corriger la description du cron ;
- documenter précisément les règles de publication manuelle ;
- décider et documenter une convention de version unique ;
- documenter l'architecture supportée et la frontière avec `BaptTF/vps-infra`.

#### Critères d'acceptation

- les versions documentées correspondent au Dockerfile ;
- la procédure décrite reproduit exactement les tags publiés ;
- aucune assertion de sécurité runtime n'est présentée comme garantie si elle dépend du dépôt d'infrastructure.

## Plan de correction proposé

### Étape 1 — Sécuriser les merges et les publications

1. Ajouter le workflow PR build + smoke tests + scan.
2. Rendre ce workflow obligatoire.
3. Restreindre l'automerge Renovate aux règles explicites et aux checks verts.
4. Empêcher un dispatch manuel de déplacer `latest` sans release.

**Résultat attendu :** aucune modification de dépendance ne peut atteindre `main` ou GHCR sans validation reproductible.

### Étape 2 — Verrouiller la supply chain

1. Ajouter la vérification d'intégrité des cinq téléchargements.
2. Pinner l'image de base par digest.
3. Pinner les Actions par SHA.
4. Générer SBOM, scan et attestation associés au digest publié.
5. Mettre à jour la base et GitHub CLI pour traiter les vulnérabilités identifiées.

**Résultat attendu :** chaque entrée de build est identifiable et vérifiée ; les critiques corrigibles sont éliminées.

### Étape 3 — Durcir le runtime dans l'infrastructure réelle

1. Vérifier PVC, HOME et persistance Devin.
2. Appliquer capabilities réduites, seccomp, no-new-privileges et rootfs read-only.
3. Préparer le volume pour un UID/GID non-root puis tester Hermes de bout en bout.
4. Auditer le service account et le RBAC kubectl.
5. Déployer l'image par digest dans `BaptTF/vps-infra`.

**Résultat attendu :** une compromission d'un outil ou de l'agent a un impact limité sur le conteneur et le cluster.

### Étape 4 — Réduire le coût de build et d'exploitation

1. Réordonner les `ARG` pour localiser l'invalidation du cache.
2. Décider si Go doit être séparé dans une image `-dev`.
3. Clarifier ou ajouter le support arm64.
4. Synchroniser README et `AGENTS.md`.

**Résultat attendu :** builds incrémentaux plus rapides, image justifiée et documentation fiable.

## Limites de l'audit

Ce dépôt ne permet pas de vérifier directement :

- le manifeste Kubernetes de production ;
- le `securityContext`, les probes et les ressources ;
- le service account et le RBAC effectifs ;
- les NetworkPolicies ;
- les permissions Infisical et les scopes des credentials runtime ;
- les permissions et propriétaires réels du PVC ;
- le digest effectivement déployé par ArgoCD ;
- la configuration interne écrite dans `/opt/data/.env` par Hermes ;
- le runtime Hermes complet avec ses secrets et services externes.

L'accès anonyme au package GHCR a retourné `403` pendant l'audit. La visibilité publique réelle du package doit donc être vérifiée séparément, même si le dépôt GitHub est public.

## Définition globale de « corrigé »

L'audit pourra être considéré comme traité lorsque :

- toutes les PR construisent et testent l'image avant merge ;
- Renovate ne fusionne qu'après checks verts ;
- les téléchargements, la base et les Actions sont épinglés et vérifiés ;
- aucune vulnérabilité critique corrigible n'est publiée ;
- un SBOM, un scan et une attestation sont liés au digest publié ;
- le runtime complet fonctionne avec un security context durci et un RBAC minimal ;
- la persistance Devin est démontrée après recréation du pod ;
- le déploiement référence un digest unique et traçable ;
- les versions et procédures documentées correspondent à la réalité ;
- la stratégie de taille (`runtime` contre `-dev`) et d'architecture est explicitement décidée.
